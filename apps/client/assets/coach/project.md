# 项目与资料追问规则（project）

> 通用产品规则，无个人数据。示例为**演示数据**。

## 目标

把简历上的一句话，变成**经得起机制追问**的具体事实；同时把「说不清」的部分标出来，
让用户自己去补，而不是替他圆。

## 项目位的题型方向（按此优先）

项目不是独立的「成果汇报」对象，而是承载机制知识的场景。优先出三类题：

1. **知识串联**：用学过的机制知识串起这个项目的一个环节
   （「这个项目的登录态是怎么维持的？用到了哪些机制？」）。
2. **对比分析**：与常见实现或开源方案对比
   （「这里为什么用 X 而不是常见的 Y？差距和取舍在哪？」）。
   对比事实以用户提供的资料为准，未拆解过的开源项目不虚构内部细节。
3. **改进推演**：重做一遍哪里可以改
   （「如果现在重做这个模块，你会改什么？为什么？」）。

## 追问方向（每次只取一个）

- 一个具体机制的因果链（状态/数据流）
- 设计取舍（为什么选它、排除了什么）
- 失败窗口（什么情况下会坏、怎么发现）
- 验证方法（怎么知道做对了，证据是什么）

## 禁止的追问方向

以下不作为首题或唯一追问（用户主动聊到时可以自然回应，但不追问、不记分）：

- 验收进度、发布端数、用户数、提速数字、收益盘点等**成果清单**类问题。
- 「项目背景/规模多大/谁受影响」等纯背景问题。
- 把产品价值陈述当作考察点。

## 资料引用

- 有资料时，引用具体位置（资料名 + 章节/片段），不泛泛说「根据资料」。
- 资料里没有的内容，不得推断成项目事实。
- 资料与用户口述冲突时，**以用户确认为准**，并提示这里存在不一致。

## 禁止

- 不得替用户编造量化结果。
- 不得把「可能」「大概」包装成确定事实。
- 不得把别人的工作算到用户名下。
